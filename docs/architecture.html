Why POC02 changes fanout to topic

POC01 uses a fanout main exchange because the original order event is intentionally broadcast to payment, inventory and warehouse queues. POC02 introduces topic routing so a retry can target only the service that originally failed.

POC02 boundary: common failed-orders queue

After the permitted automatic retries are exhausted, the message is moved to poc2.common.failed.orders.queue. This is the end of POC02. POC02 does not attempt another recovery cycle from this queue. A future POC03 can introduce a dedicated failed-order reprocessing service.

Same exchange name and idempotent declaration

If several applications declare poc2.order.events with compatible settings, they are declaring the same RabbitMQ exchange, not creating separate exchanges. The exchange type is part of the declaration contract.

POC01 to POC02: POC01 uses order_exchange as fanout, while POC02 uses the separately named poc2.order.events as topic. The POC02 naming convention also makes the new topology easy to identify in the Management UI.

Why not exchange-per-service?

An exchange-per-service/domain design is also valid and can provide stronger domain ownership. POC02 intentionally focuses on a shared event exchange with explicit topic routing so the retry-routing concept is easy to see. A later POC can demonstrate service/domain-owned exchanges.

UI visibility mode

Consumers use prefetchCount=1. The two-second service processing delay and three-second reprocessor retry delay are intentionally enabled under explicit demonstration regions so message movement can be observed in RabbitMQ Management UI. These delays are demonstration aids, not production processing settings.

Local topology reset

POC01 and POC02 use different main exchange names, so they can coexist. For a clean POC02 Management UI demonstration, remove or purge the old POC01 topology first. There is no need to delete the RabbitMQ Docker volume just to switch POCs.

Public repository

RabbitMQ connection settings are loaded from .env. The actual file is ignored by Git and .env.example contains placeholders. No real production or shared credentials should be committed.
